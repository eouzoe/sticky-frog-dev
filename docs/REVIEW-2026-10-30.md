## 0. 從專案誕生就錯、而且被我照單全收的判斷

這些不是 bug，是前提。前提錯了，底下的優化都是在補洞。

1. **背景是「散佈的 3D 道具」**：森林 80 多棵樹、山、雲、蘆葦各自是一張半透明公告板，每幀重新投影、排序、畫上去。這是 three.js 場景的思路，搬到 2D 之後是最壞的做法：填充量最大、CPU 最忙、而且畫面只是隨機撒的綠色團塊，沒有構圖、沒有輪廓設計、沒有光影整合，看起來廉價。我為了「像原版」把密度、深度帶、霧都照抄，等於照抄了錯誤。
2. **水和天空是逐像素著色器**：水面做光線求交、波浪法線、太陽高光、菲涅耳；天空做星星、極光。這是寫實渲染的做法，放在卡通風格裡不但貴，還不好看：卡通水面應該是平塗加幾條高光帶。
3. **鏡頭透視套在所有東西上**：遊戲平面本來就在 z=0，鉤子、荷葉、角色根本不需要透視；透視只對背景視差有意義，而視差用固定比例的捲軸就能得到。
4. **開機 = 把所有東西載完再出選單**：主程式 187 KB（gzip 67 KB）包含商店、成就、排行、結算、遙測、自動玩家、全部造型設定、全部音效定義。選單第一幀只需要模擬、渲染核心、選單畫面。
5. **選單要等 SDK**：網頁版最多 2.4 秒、CrazyGames 網域最多 8 秒。第一幀 60 ms 就畫出來了，玩家卻在等一個跟畫面無關的初始化。
6. **資源分配本末倒置**：這是一個盪來盪去的闖關遊戲，核心是鉤子、荷葉、危險物、角色和手感。大部分效能和美術預算卻花在背景上，而背景跟玩法沒有互動，還因為太亮太雜在搶玩法層的可讀性。
7. **畫質分級 = 降 DPR**：最貴的水面、天空、背景數量、120 Hz 物理都不分級；降 DPR 在 CPU 受限時只是白白變糊。
8. **主模組是上帝模組**：main.ts 650 行，狀態機、輸入、存檔、計分、事件轉手感、鏡頭、教學、測試掛鉤全在一起；全域 `G` 近 60 個欄位。渲染會改模擬狀態。
9. **音效每播一次建一組 WebAudio 節點**：零資源位元組的優點保留，但播放方式是錯的。

物理極限：首訪走 HTTPS 要 3–4 個往返才拿到 HTML，TCP 慢啟動初始窗口約 14 KB，206 KB 還要約 4 個往返。往返 40 ms 時光往返就約 0.3 s；行動網路往返 70–150 ms 是 0.5–1.2 s。**往返超過約 60 ms，首訪就算全部內嵌進一個 HTML 也做不到 0.3 s。** 重複造訪要靠雜湊檔名＋長效快取（HTML 本身仍要 1 個往返，除非 SW 可用），加上把低階機的 CPU 開機預算壓到約 250 ms：JS < 60 ms、樣式版面 < 30 ms、GL 上傳 < 50 ms。

審查代理的量測腳本在 scratchpad/arch/（measure.mjs 時間線、trace.mjs 主執行緒拆解、cov.mjs 逐模組覆蓋率、enc/run.sh 圖集格式比較），可重跑。

## 6. 方向（待討論，不是結論）

- 背景改成每個世界 3–5 層**設計過的**視差層（遠景輪廓、中景樹群、近景前景），離線合成一次、執行時每層一個四邊形。目標：每幀填充 ≤ 2 個螢幕、四邊形 ≤ 20、背景 CPU ≈ 0。畫面上要同時解決可讀性：背景降對比、降飽和，讓玩法層跳出來。
  → **結構已換（2026-10-30）**：層在載入世界時用現有烘焙零件合成長條，每幀每層一個四邊形；精靈填充 3.35 → 0.5 個螢幕、背景每幀零計算。內容還是原本那批零件的隨機擺放，構圖設計是下一步。
- 水面改平塗加高光帶，天空改頂點色漸層，兩個全螢幕著色器通道歸零。→ **已做**。
- 預算反過來分配：核心玩法物件（鉤子、荷葉、危險物、角色、舌頭）的輪廓、動畫、回饋優先。
- 開機核心只含模擬、渲染核心、選單；其他延後。永遠不等 SDK。重複造訪走 Service Worker。
- 單向資料流：平台 → 應用狀態 → 模擬（純） → 渲染／UI 只讀；計分變成 reduce(run, event) → effects；狀態機顯式。
- 音效開機後離線算成緩衝，播放一個節點。
- 分級改像素預算，並用 JS 時間判斷受限的是哪一邊。
